# Обращение 1

## Причина

Дело в том что устройство с `id=6`, а если точнее с серийным номером `SN-0406` ещё не выходило на связь __ни разу__, поэтому и при выгрузке heartbeat-файла о нём нет записи.  
В связи чем при запросе получения ответа о нём возникла ошибка при форматировании ответа. Ведь функция `device_to_dict` вызывала `fmt_ts`, чтобы преобразовать время (`last_seen`) в нужный формат. Однако вместо строки функция `fmt_ts` получила неожиданное значение `None`, что приводило к некорректному форматированию.

## Как искал

*Ошибку можно было найти в __[logs/app.log](logs/app.log)__*  
Внутри лога обнаружил цепочку ошибок, который приводил к нашей ошибке, и там уже было видно, в каком файле, в каком строке, по какой причине произошла ошибка.*

Так же нужно было понять почему значение в Базе Данных равняется `null`, как оказалось что в [файле](data/heartbeats_2026-08-21.json) не было ни одной записи от данного устройства. Поэтому значение так и осталось не изменненной как при его создании.

## Исправление

Поскольку переменная `last_seen` может быть как строкой, так и `null`, необходимо было добавить проверку в функцию `fmt_ts`. Если переменная не является строкой, функция должна возвращать `None`.

## Проверка

Так же проверяем какие функции вызывают `fmt_ts`, чтобы исключить ошибки в других частях кода.


Ответ на запрос `/devices/6`

```json
{
  "id": 6,
  "serial": "SN-0406",
  "site": "Полигон Север",
  "model": "KDX-Cam2",
  "installed_at": "2026-08-19",
  "last_seen": null,
  "open_tickets": 0
}
```

# Обращение 3

## Причина

Дело в том что логика в таких случаях есть, но не было явного указания того какой статус возвращать при ошибках, ведь по умолчанию любой ответ от сервера это статус `200`, что обозначает __успех__.

## Как искал

Ищем ручку которая отвечает за создание обращения и узнаем что это `/tickets` методом `POST`.  
Видим логигу которая отвечает за проверку корректности веденной пользователем серийного номера. Его и нужно доделать правильно.

## Исправление

Укажем явный статус `422` в ответе при возниновении данной ошибки, используя готовые константы стаусов ответов от `fastapi`. Так же добавим их в других частях кода для сохранения одного стиля.

## Проверка

При запросе:

```bash
curl -X 'POST' \
  '{BASE_URL}/tickets' \
  -H 'accept: application/json' \
  -H 'x-api-key: {API_KEY}' \
  -H 'Content-Type: application/json' \
  -d '{
  "serial": "TestSerial",
  "title": "Test title",
  "description": "Test description"
}
```

Получаем ответ:

```bash
{
  "detail": {
    "error": "device not found",
    "serial": "TestSerial"
  }
}
```

А в логах видим:
```bash
INFO:     {IP:PORT} - "POST /tickets HTTP/1.1" 422 Unprocessable Content
```
